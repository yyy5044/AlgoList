## 2. 주제별 계획

각 주제는 **알아야 할 것 → 볼 자료 → 방어할 질문 → 완료 기준** 순서다.

### A. 데이터 소스와 응답 구조

**알아야 할 것**
- 왜 Hugging Face인가: 코드포스는 문제 본문 API가 없고 크롤링이 막혀 있음. 대회 문제가 CC-BY-4.0으로 `open-r1/codeforces` 데이터셋에 공개됨.
- datasets-server `rows` API: `offset`, `length` 파라미터, `length` 상한 100, 응답 형태 `{ "rows": [ { "row_idx", "row": {...} } ], "num_rows_total" }`.
- 행 하나의 27개 필드 중 무엇이 무겁고 무엇을 쓰는지. 행 크기가 극단적으로 편중돼 있다는 사실.
- 서버가 필드를 골라서 내려주는 옵션이 있는지 (없으면 클라이언트에서 버릴 수밖에 없다는 논리).

**볼 자료**
- `CodeforcesPageReader.java:43` (URL), `:61` (`KEEP`)
- 직접 호출해 보기: `length=1`로 한 행 받아서 필드 훑어보기

**방어할 질문**
- 왜 이 데이터셋을 골랐나? 라이선스는?
- 응답에 어떤 필드가 있고 왜 10개만 쓰나?
- 어떤 필드가 무거웠나? 얼마나?
- 서버에서 필요한 필드만 받을 수는 없었나? parquet 파일을 직접 받는 방법은?

**완료 기준**: 응답 JSON 구조를 종이에 그릴 수 있고, "행 하나가 107MB였고 그중 내가 쓰는 건 1.8KB"를 말할 수 있다.

### B. Spring Batch chunk 모델 (그림 상단)

**알아야 할 것**
- Job, Step, chunk 지향 처리의 의미. Reader는 한 건씩 반환, Writer는 chunk 단위로 받음, chunk 하나가 트랜잭션 하나.
- 이 프로젝트의 chunk 크기 = page 크기 = 100 이라는 불변식과 그 이유.
- `ItemStreamReader`의 `open / read / update / close` 호출 시점.
- `@StepScope`가 왜 필요한가.
- `faultTolerant().skip().skipLimit()`의 동작.
- 메타데이터 테이블과 `ExecutionContext`.
- OOM이 Reader에서 났다는 것의 근거 (스택트레이스가 read 단계).

**볼 자료**
- `CodeforcesIngestJobConfig.java:53~61`
- `CodeforcesPageReader.java:94` (open), `:106` (read), `:127` (nextAvailablePage), `:160` (update)
- `CodeforcesParser.java:26`, `ProblemItemWriter.java`
- 이 대화의 앞부분 (재시작 설계 설명)

**방어할 질문**
- chunk가 뭐고 왜 chunk로 처리하나? 한 건씩 커밋하면 안 되나?
- chunk 크기를 줄이면 왜 메모리가 줄 것이라고 기대했나? 왜 안 줄었나?
- Reader가 한 건씩 반환하는데 왜 한 페이지를 통째로 들고 있나?
- Processor는 뭘 하나? 왜 Reader에서 바로 DTO를 안 만들었나?

**완료 기준**: 그림 상단을 보지 않고 다시 그릴 수 있고, 각 화살표에서 무엇이 얼마나 메모리에 있는지 말할 수 있다.

### C. JVM 힙과 서버 메모리 (헤더, 500MiB 점선, swap)

**알아야 할 것**
- 힙이 무엇이고 힙 외 메모리(메타스페이스, 스레드 스택, 다이렉트 버퍼)와 어떻게 다른가.
- 최대 힙 기본값이 물리 메모리의 1/4인 이유와 확인 방법 (`-XX:MaxRAMPercentage`, `java -XX:+PrintFlagsFinal`).
- 컨테이너 안의 JVM이 메모리를 어떻게 인식하나 (cgroup 제한이 없으면 호스트 메모리 기준).
- `OutOfMemoryError: Java heap space`가 나는 조건, Full GC, GC가 회수하지 못하는 살아 있는 객체.
- swap이 무엇이고, 왜 swap을 늘려도 최대 힙 기본값은 그대로인가. 그렇다면 swap은 무엇에 도움이 되나.
- `-Xmx`를 직접 올리는 선택지와 그 위험 (힙이 물리 메모리를 넘으면 스왑 스래싱, OOM Killer).
- 개발 PC에서는 왜 멀쩡했나.

**볼 자료**
- `backend/Dockerfile:26` (힙 옵션 없음), `docker-compose.yml` (메모리 제한 없음)
- `README.md:131~133` (t3.small, swap 2GiB)

**방어할 질문**
- 힙이 왜 500MB였나? 직접 확인했나?
- swap을 늘렸는데 왜 효과가 없었나?
- 그럼 `-Xmx1g`로 올리면 되지 않았나? 왜 안 했나?
- 인스턴스를 더 키우면 되지 않나?
- 개발 환경과 운영 환경 차이를 왜 미리 못 잡았나?

**완료 기준**: "물리 메모리, swap, 힙 상한"의 관계를 그림으로 설명할 수 있고, `-Xmx`를 올리지 않은 이유를 한 문장으로 말할 수 있다.

### D. Before: 왜 터졌나 (메모리 해부)

**알아야 할 것**
- 수정 전 코드 두 줄의 의미: `retrieve().body(String.class)`, `objectMapper.readTree(response)`.
- 그 순간 힙에 동시에 올라가 있는 것들: 수신 바이트 버퍼, 응답 String, JsonNode 트리, 하류 chunk가 붙잡고 있는 원본 행 노드.
- Java String의 메모리 표현 (문자당 1바이트 또는 2바이트)과 JsonNode 트리의 객체 오버헤드. 그래서 원본 크기의 몇 배가 필요한지.
- chunk를 10으로 줄여도 터진 이유: 행 크기가 편중돼 있어서 무거운 행 하나(107MB)가 어느 chunk에든 들어가면 그 chunk가 터진다.
- 재현에서 왜 6번째 페이지(offset 500)에서 터졌나: 그 페이지가 143MB이고 107MB짜리 행이 들어 있다.

**볼 자료**
- `git show f1aea71:backend/src/main/java/com/algolist/backend/problem/batch/codeforces/CodeforcesPageReader.java` 의 `fetchPage`, `requestWithRetry`
- `docs/test/codeforces-batch-heap-test-report.md` 1절, 3.2절

**방어할 질문**
- 응답이 143MB인데 왜 힙이 1.5GB나 필요했나?
- chunk를 줄였는데 왜 여전히 OOM인가?
- 정확히 어느 줄에서 터졌나? 어떻게 알았나?
- 메모리 문제라는 건 어떻게 확신했나?

**완료 기준**: "143MB 응답 → String → 트리 → chunk" 각 단계에서 힙에 무엇이 남는지 순서대로 말할 수 있고, chunk 축소가 실패한 이유를 107MB 행으로 설명할 수 있다.

### E. After: 스트림 파싱 코드

**알아야 할 것**
- `RestClient`의 `exchange()`와 `retrieve().body()`의 차이. 응답 본문을 `InputStream`으로 받는다는 것의 의미.
- Jackson 스트리밍 API: `JsonParser`, `JsonToken`, `nextToken()`, `currentName()`, `skipChildren()`. 트리 모델, 데이터 바인딩과의 차이.
- `parseRows`와 `extractSlimRow`를 한 줄씩: 최상위 객체 → `rows` 배열 → wrapper → `row` → 필드별로 유지 또는 폐기.
- `KEEP` 필드에만 `readTree(p)`를 쓰는 이유 (부분 트리는 작다).
- 수정 후에도 힙에 남는 것: 슬림 노드 100건 리스트. 그래서 메모리가 "필요한 필드 × 건수"로 결정된다.
- `skipChildren()`이 107MB를 건너뛸 때 실제로 일어나는 일 (스트림에서 읽기는 하지만 객체를 만들지 않음).
- 에러 처리: 콜백 안에서 5xx, 429를 재시도 예외로 바꾸는 이유, 백오프, 요청 간격.

**볼 자료**
- `CodeforcesPageReader.java:186~212` (요청과 재시도), `:220~250` (parseRows), `:256~279` (extractSlimRow)
- 커밋 `7a8fe03` 의 diff

**방어할 질문**
- 스트림 파싱이 뭔가? 기존 방식과 무엇이 다른가?
- `skipChildren()`은 정말 메모리를 안 쓰나? 네트워크로는 다 받지 않나?
- 왜 DTO로 바로 역직렬화(`@JsonIgnoreProperties`)하지 않았나? 그것도 필요한 필드만 남기지 않나?
- 한 행의 `description`이 엄청 크면 어떻게 되나?
- 응답을 읽는 동안 HTTP 연결은 어떻게 되나?
- 한 페이지를 리스트로 모으지 않고 한 건씩 흘려보낼 수는 없었나?

**완료 기준**: `parseRows`와 `extractSlimRow`를 코드 없이 의사코드로 다시 쓸 수 있다.

### F. 원인을 좁힌 과정과 대안 비교

**알아야 할 것**
- 각 시도가 어떤 가설을 검증한 것인지: swap(메모리 총량 가설), 인스턴스 변경(힙 상한 가설), chunk 축소(건수 가설).
- 세 가지가 모두 실패했다는 사실에서 "건수가 아니라 읽는 방식"으로 넘어간 추론.
- 고려할 수 있었던 대안과 각각을 고르지 않은 이유:
  - `-Xmx` 상향 / 더 큰 인스턴스
  - page-size를 1로
  - 데이터 바인딩으로 필요한 필드만 매핑
  - parquet 파일을 받아 로컬에서 변환
  - 무거운 행만 건너뛰기
- 당시에는 정량 측정 없이 배포했고, 나중에 재현 테스트로 수치를 확인했다는 사실.

**볼 자료**
- 1.1절 경과표, 커밋 `48c577f`, `e1dc54f`, `7a8fe03`, `856fe6f`
- 노션 "1학기 관통 프로젝트 발표 준비" (6/25 작성, 당시 경과의 1차 기록)

**방어할 질문**
- 처음에 무엇을 의심했고 왜 그 순서로 시도했나?
- 힙 덤프나 GC 로그는 봤나? (당시에는 안 봤다. 솔직하게)
- 지금 다시 한다면 무엇부터 하겠나?
- 가장 간단한 해결책(메모리 증설)을 두고 왜 코드를 고쳤나?

**완료 기준**: 경과를 1분 안에 말할 수 있고, 대안 다섯 가지 각각에 대해 "왜 아닌지"를 한 문장으로 답할 수 있다.

### G. 측정과 검증 (1,570MB → 105MB)

**알아야 할 것**
- 측정 설계: 파싱 방식만 다른 두 브랜치, 같은 입력 3,000건, 시스템 프로퍼티로 조건 통일.
- 배치를 테스트 안에서 동기 실행한 이유. `-Xmx`와 `-Xlog:gc*`.
- "피크 힙(GC 직전)"과 "피크 잔존(GC 직후)"의 차이, 커밋된 힙의 의미.
- 4회 실행 결과표를 읽는 법. 왜 before를 2GB로 한 번 더 돌렸나.
- 측정의 한계: 로컬 Windows, 전체의 약 30%, 각 1회, 운영 서버에서 잰 값이 아님.

**볼 자료**
- `docs/test/codeforces-batch-heap-test-report.md` 전체
- `BatchMeasurementTest.java` (로컬, `measurement` 브랜치에도 있음)
- 브랜치 `perf-before`, `perf-after`

**방어할 질문**
- 1,570MB는 어떻게 잰 값인가? 운영에서 잰 건가?
- 15배라는 숫자는 어떤 조건에서 나온 건가?
- 3,000건만 돌렸는데 전체에서도 같다고 할 수 있나?
- 한 번 측정으로 충분한가?
- 운영에서는 고쳐진 걸 어떻게 확인했나?

**완료 기준**: 결과표 4행을 각각 "왜 이 조건으로 돌렸는지"와 함께 설명할 수 있다.

### H. 주변 설계 (그림에는 없지만 이어서 나오는 질문)

**알아야 할 것**
- 실패 지점부터 재시작: offset 체크포인트, 같은 Job 인스턴스 재실행.

### J. 한계와 개선안 (먼저 말하면 강점이 되는 것)

**정리해 둘 것**
- 힙 상한을 명시하지 않고 기본값에 의존하고 있음.
- 수정 당시 정량 측정과 힙 덤프 없이 추론으로 고쳤음.
- 수정 후에도 한 페이지의 슬림 노드를 리스트로 모음. `KEEP` 필드 자체가 큰 행에는 여전히 취약.
- 무거운 필드를 버려도 네트워크로는 전부 받음 (전송량과 시간은 그대로).
- 운영 메모리 모니터링과 알림이 없음.
- 실패 페이지는 기록만 하고 자동 재수집하지 않음.

**완료 기준**: "아쉬운 점이 뭐냐"는 질문에 세 가지를 바로 답하고, 각각의 개선 방향을 말할 수 있다.

## 4. 직접 해볼 실습

읽기만 하면 꼬리질문에서 무너진다. 아래는 직접 손으로 확인한다.

1. **응답 구조 보기**: `length=1`로 한 행을 받아 27개 필드와 크기를 확인한다.
2. **무거운 행 찾기**: offset 566 한 행을 받아 `official_tests`가 100MB를 넘는 것을 확인한다.
3. **기본 힙 확인**: 로컬에서 `java -XX:+PrintFlagsFinal -version` 으로 `MaxHeapSize`를 보고 물리 메모리의 1/4인지 계산해 본다.
4. **OOM 재현**: `perf-before` 브랜치에서 `-Xmx512m`로 `BatchMeasurementTest`를 돌려 6번째 페이지에서 터지는 것을 본다.
5. **수정 후 완주**: `perf-after` 브랜치에서 `-Xmx128m`로 돌려 완주하는 것을 본다.
6. **GC 로그 읽기**: 두 실행의 GC 로그에서 피크 값을 직접 뽑아 보고서 수치와 맞는지 확인한다.
