# 디버깅 기록 작성 규칙

기록은 **나중에 같은 문제를 다시 만났을 때 30초 안에 "뭐가 문제였고 뭘 바꿨는지" 알아보는 용도**다. 설명보다 코드, 코드보다 변경 지점이 우선이다.

## 위치와 파일명

- 경로: 프로젝트 최상단 `notes/debug/<문제-핵심>.md`
- 파일명은 kebab-case 영문. 문제의 핵심 명사로 짓는다. 예: `batch-transaction-manager.md`
- 파일 하나 = 문제 하나. 비슷한 문제라도 원인이 다르면 파일을 나눈다.

## 구조 (이 순서 그대로)

```markdown
# <문제 핵심 제목>

**문제 상황**: <쉬운 말로 두세 문장. ① 어떻게 알게 됐나 ② 뭐가 잘못돼 있었나 ③ 그래서 뭐가 안 되나 (지금까지 괜찮았다면 왜 괜찮았는지)>

**수정한 파일**: `<저장소 기준 상대 경로>`

## 원래 코드

```java
...
```

## 수정 코드

```java
...
```

<선택: 왜 이렇게 고치는지 한두 줄>
```

- 수정한 파일이 여럿이면 "**수정한 파일**"부터 "수정 코드"까지를 파일마다 반복한다.
- "문제 상황"은 전문 용어를 설명 없이 쓰지 않는다. 3개월 뒤의 내가 읽어도 바로 이해되는 문장이어야 한다. 세 문장을 넘기지 않는다.
- 마지막 설명은 두 줄 이내. 없어도 된다.

## 접기 규칙 (원래 코드 / 수정 코드)

변경 지점만 펼치고 나머지는 접는다. 목적은 두 블록을 나란히 놓았을 때 **다른 줄이 곧 변경 내용**이 되게 하는 것이다.

1. 바뀐 줄과, 그 줄이 어디 붙어 있는지 알려주는 선언(메서드 시그니처, 클래스 선언)만 보여준다.
2. 바뀌지 않은 매개변수 목록은 `(...)`, 바뀌지 않은 본문은 `{...}`로 접는다.
3. 원래 코드와 수정 코드에서 접은 부분은 **같은 모양**이어야 한다. 한쪽만 펼치면 비교가 안 된다.
4. 바뀐 줄이 본문 안에 있으면 그 줄 앞뒤 한두 줄만 펼치고 나머지는 `...` 한 줄로 접는다.
5. import는 새로 추가되거나 바뀐 것만 적는다. 기존 import는 생략한다.

예: 메서드 위에 어노테이션 하나를 추가한 경우

```java
// 원래
@Bean
PlatformTransactionManager batchSystemTransactionManager(...) {...}

// 수정
@Bean
@BatchTransactionManager
PlatformTransactionManager batchSystemTransactionManager(...) {...}
```

## 쓰지 않는 것

- 디버깅 과정, 시도했다 실패한 것, 검증 방법. 필요하면 별도 문서로.
- 코드 전체 복사. 접기 규칙을 어기는 가장 흔한 실수다.
- 주석만 바뀐 파일. 기록 가치가 없으면 뺀다.
